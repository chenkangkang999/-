## 一、技术方案总览（层次选型）

| 层次 | 选型 |
| ---- | ---- |
| 后端 | Django + DRF + Django Channels（WebSocket） |
| 前端 | Vue3 + Vite + Pinia + Vue Router + ECharts + Element Plus |
| 业务库 | PostgreSQL |
| 缓存/队列 | Redis + Celery |

| 部署 | Docker Compose（Django + Vue3 + Redis + Milvus + PostgreSQL） |

## 二、新增功能（创新点）

1. **数据飞轮 + 混合检索**：反馈回流 → RAG 评估 → 微调，形成「用反馈持续提升检索质量」的闭环
2. **hash 去重**：索引前对文档/切片计算内容指纹，重复内容只入库一份
3. **Milvus 全量检索**：所有医学文档切片入库，全量向量检索
4. **稠密 + 稀疏检索**：BGE 稠密向量与 BM25 稀疏向量融合，取长补短
5. **Docker Compose 部署**：多服务一键编排（Django + Vue3 + Redis + Milvus + PostgreSQL）

## 三、RAG 检索工程

- **Milvus 全量索引**：所有医学文档切片入库
- **BGE-M3 embedding**：LoRA 微调，微调前后做 Recall@K 对比实验
- **混合检索**：BGE 稠密向量 + BM25 稀疏向量融合

- **RAG 评估**：Recall@K / MRR / NDCG

## 六、数据资产与数据处理（实测）

数据落盘于 `data/raw/`（原始）与 `data/processed/`（清洗后），清洗脚本在 `scripts/`。

### 原始数据（data/raw/，共 268MB）

| 数据源 | 内容 | 规模 | 用途 |
| ------ | ---- | ---- | ---- |
| cMedQA2 | 中文社区医疗问答 | 12 万问题 + 22.6 万答案 + 500 万条 (query, pos, neg) 三元组 | BGE LoRA 微调训练对 |
| chinese-medical-kg | 中文医学知识图谱 | NMPA 国产药品 16.4 万 + 进口 3,141 + ICD-10 35,862 + TTD 药物-靶点-疾病 | 中文药名映射 + 疾病编码 + 适应症 |
| DDInter 2.0 | 药物相互作用（英文药名 + 严重级别） | 8 个 CSV 共 222,391 条 DDI | 用药 Agent 相互作用检查 |
| Framingham | 心血管 10 年风险 | 4,240 条 × 16 字段 | 风险评估 Agent 慢病评分 |

### 清洗后数据（data/processed/，共 118MB）

| 文件 | 规模 | 说明 |
| ---- | ---- | ---- |
| cmedqa2/train_triplets.jsonl | 9 万条（66MB） | 微调训练集 (query, positive, negative) |
| cmedqa2/val_triplets.jsonl | 1 万条（7.3MB） | 微调验证集 |
| drugs/ddi_clean.csv | 160,235 条 | DDI 去重后（含中文药名列） |
| drugs/icd10.csv | 35,862 条 | ICD-10 疾病编码（code / name） |
| drugs/nmpa_domestic.csv | 164,477 条 | NMPA 国产药品表 |
| drugs/nmpa_import.csv | 3,141 条 | NMPA 进口药品表 |
| framingham_clean.csv | 4,240 条 | 慢病风险数据（缺失值已填充） |

### 数据处理流程

| 数据源 | 处理方式 |
| ------ | -------- |
| cMedQA2 | 取 train 三元组 (question_id, pos_ans_id, neg_ans_id) → join question.csv + answer.csv → 构造 (query, positive, negative) → 采样 10 万条（train 9 万 / val 1 万） |
| DDInter | 8 CSV 合并 → 按 (Drug_A, Drug_B) 去重（保留最严重 Level）→ 英文药名映射中文（常见药覆盖，罕见靶向药/单抗/疫苗保留英文） |
| chinese-medical-kg | ICD-10 导出 code/name；NMPA 表 header=1 读取（Excel 表头在第 2 行） |
| Framingham | \r\n 换行符转 \n → NA 转 NaN → 中位数填充（缺失 645 → 0） |

### hash 去重（数据指纹）

- **实现**：`rag/dedup/hash.py`
- **算法**：`normalize_text`（NFKC 归一化 → 空白折叠 `\s+`→单空格 → strip → lower）→ sha256
- **作用**：索引前对文档/切片计算内容 hash，重复内容只入一份；同一段文字仅空白/大小写差异不重复入库
- **与结构化去重的区别**：DDInter 用 (Drug_A, Drug_B) 药对去重（结构化去重）；hash 去重用于 RAG 文档切片（文本内容去重）

## 七、LoRA 微调实验（微调前后 Recall@K 对比）

- **流程**：BGE-M3 基座 → LoRA 微调 → 同测试集评测 → 生成对比实验表
- **评测指标**：Recall@1 / Recall@5 / Recall@10、MRR、NDCG@10

### 基线 vs 调优参数对比

| 参数 | 第一轮基线 | 第二轮调优 | 调优理由 |
| ---- | ---------- | ---------- | -------- |
| 学习率调度器 | linear | cosine（余弦退火） | 收敛更平滑，接近最优时减少震荡 |
| 权重衰减 | 0.0 | 0.01 | AdamW 的 L2 正则，防小数据 + 多 epoch 过拟合 |
| epochs | 1 | 2 | 1 epoch 略欠拟合，配早停防过拟合 |
| 有效 batch | 16 | 16（保持） | 8 × 梯度累积 2 |
| 学习率 | 2e-4 | 2e-4（保持） | LoRA 最佳区间 1e-4 ~ 5e-4 |
| warmup | 0.1 | 0.1（保持） | 与 cosine 组成「动态学习率」曲线 |
| 动量 β1 / β2 | 0.9 / 0.999 | 0.9 / 0.999（保持） | AdamW 默认即最优，LoRA 不调 |
| 早停 | 无 | patience=3 | 验证集 eval_loss 连续 3 次无改善即停 |

### 早停方案（transformers EarlyStoppingCallback）

| 项 | 取值 | 说明 |
| -- | ---- | ---- |
| 监控指标 | 验证集 eval_loss | MultipleNegativesRankingLoss 在验证集上的对比学习损失 |
| patience | 3 | 连续 3 次评测无改善即提前停止 |
| threshold | 1e-4 | loss 改善 < 1e-4 视为无改善（忽略噪声波动） |
| 评测频率 | eval_steps=100 | 2 epoch 约 2500 步，共约 25 次评测，能及时捕捉过拟合 |
| 最优落盘 | load_best_model_at_end=true | 训练结束自动加载验证集最优 checkpoint，与早停配合 = 最优模型自动保存 |

### 三组消融对比表（实测结果）

| 配置 | Recall@1 | Recall@5 | Recall@10 | MRR | NDCG@10 |
| ---- | -------- | -------- | --------- | --- | ------- |
| 基座 BGE-M3（零样本） | 0.8470 | 0.9810 | 0.9930 | 0.9035 | 0.9254 |
| LoRA（linear + wd=0 + 1ep，基线） | **0.8680** | 0.9830 | 0.9950 | **0.9190** | 0.9378 |
| LoRA（cosine + wd=0.01 + 2ep + 早停，调优） | 0.8660 | 0.9820 | 0.9950 | 0.9184 | 0.9373 |

> **结论**：余弦调优未超线性基线，生产选型保留线性基线配置（linear + wd=0 + 1ep）。这证明在「小数据 + 强基座」场景下，LoRA 增益主要来自对比学习适配本身，优化器超参无额外收益；同时验证了早停机制能正确捕捉「验证集损失回升」并自动止损。

### 9.1 正式部署（Docker Compose 多容器）

| 服务 | 说明 |

### 9.2 创空间部署（Docker 单容器 CPU 演示版）

系统以 Docker 打包方式部署到魔搭 ModelScope 创空间（单容器 CPU 演示版），用于答辩/演示展示完整流程链路。

#### 部署形态

| 项 | 方案 |
| -- | ---- |
| 目标平台 | 魔搭 ModelScope 创空间（免费 2 核 CPU + 16G 内存，无 GPU） |
| 打包方式 | Docker 单容器（前端 + 后端合一） |
| 监听端口 | 7860（创空间固定端口） |
| 镜像体积 | 约 300~400MB（纯 Python 依赖，无重依赖） |

#### 关键设计：避开大依赖，保证打包/提交快

系统训练依赖 torch（约 2.5GB）和 BGE-M3 模型（2.2GB）体积巨大，直接打进镜像会又大又慢。演示版通过「依赖分级 + 运行时降级」避开：

| 依赖 | 处理 |
| ---- | ---- |
| torch / sentence-transformers / pymilvus | 不进镜像（只在 `requirements/ai.txt`，标注按需安装） |
| BGE-M3 模型（2.2GB） | 不进镜像，运行时按需下载或降级 |
| 原始数据（268MB） | `.dockerignore` 排除，不进镜像 |
| 前端 node_modules | 本地 build 成 dist 后只 COPY 产物 |

运行时服务降级（`config/settings/demo.py` + `base.py` 已有开关）：

| 生产服务 | 演示版降级 |
| -------- | ---------- |
| PostgreSQL | SQLite |
| Redis | LocMem 内存缓存 |
| Celery 异步 | 同步执行（`CONSULTATION_EXECUTOR=sync`） |
| Milvus 向量检索 | BM25 稀疏检索（CPU） |
| Vue3 前端 | whitenoise 直接托管（SPA fallback） |

#### 落地文件

| 文件 | 作用 |
| ---- | ---- |
| `Dockerfile` | python:3.12-slim 单容器，只装 prod.txt（无 torch），daphne 监听 7860 |
| `config/settings/demo.py` | 通道层内存化 + whitenoise 前端托管 + SPA fallback + 禁用 CSRF + 移除 XFrameOptions（供 iframe 嵌入） |
| `ms_deploy.json` | 创空间部署配置（docker SDK + 2v-cpu-16g-mem + 端口 7860） |
| `.dockerignore` | 排除 models/data/node_modules 等大目录，只放行 frontend/dist |

#### 部署流程

1. 本地 `npm run build` 产出 `frontend/dist`
2. `git push` 到创空间仓库（master + main 双分支）
3. 创空间页面「重新构建/部署」→ 云端 build（纯 Python 依赖，约几分钟）→ 起服务监听 7860
